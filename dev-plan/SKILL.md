# Dev Plan

目的: 曖昧な要望を「実行可能な開発プラン」に落とし込む。

## 入力の取り方（不足があれば先に聞く）

最初に、足りない情報を最小限だけ質問する（多すぎない）。

- 何を作る/直す？（ゴール、成功条件）
- 制約は？（期限、予算、技術スタック、互換性、運用要件）
- スコープ外は？（やらないこと）
- 既存資産は？（リポジトリ、API、DB、仕様、デザイン）
- 期待する粒度は？（1週間のタスク粒度 / エピック粒度 / ADRまで）

不明点が多い場合は、仮定（Assumptions）を明示して進め、ユーザーに確認する。

## 出力の原則

- 具体: 「やること」を成果物/変更点ベースで書く（例: `POST /v1/foo` 追加）。
- 分割: 大きい作業は 0.5〜2日程度のタスクに分割（要望が荒い場合はエピック→タスクの2段階でもよい）。
- 依存: 依存関係とクリティカルパスを明示する。
- 検証: それぞれの段階にテスト/検証方法を付ける。
- リスク: 失敗しやすい点と回避策（計測/ロールバック含む）を書く。

## 計画の型（テンプレ）

基本セクションは以下を使い、必要に応じて省略/追加する。

1. **概要**（1〜3行）
2. **目的 / 成功条件**
3. **スコープ**（In / Out）
4. **前提**（Assumptions）
5. **設計方針**（必要なら）
6. **作業分解**（WBS: タスク、優先度、見積、担当/役割）
7. **マイルストーン**（日付があるなら絶対日付で）
8. **テスト計画**
9. **リリース/移行計画**（段階的、フラグ、ロールバック）
10. **リスク & 監視**（メトリクス、アラート、運用）

詳細テンプレは `references/templates.md` を参照。

## `update_plan` ツールの使い方（Codex 内部運用）

計画を作る/更新する作業中は `update_plan` を使って進捗を可視化する。

- 各ステップは 1 文、5〜7語程度（短く検証可能に）
- 状態は `pending` / `in_progress` / `completed`
- `in_progress` は常に 1 つだけ
- 理解が変わったら、plan を更新してから作業を続ける

## 仕上げのチェック

- スコープが曖昧なら In/Out を追加したか
- 見積の根拠（サイズ感）があるか
- 依存と順序が妥当か
- テストとロールバックがあるか
- 次のアクションが 1 行で分かるか
